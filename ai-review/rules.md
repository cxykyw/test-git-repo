# AI 代码审查规则（随代码版本走，改动请走 MR）

## 输入格式说明
每次审核任务的输入由若干"文件段"组成，每段包含：
- `[变更 diff]`：该文件的 git diff（hunks），`+` 为新增/修改行，`-` 为删除行
- `[上下文 ...]`：HEAD 上变更 hunk 周边的代码窗口，`行号| 内容` 中的行号即文件真实行号，
  发现项的 line 字段必须使用真实行号；上下文仅帮助理解，除非确有问题，不要审查纯上下文行
- `[静态扫描线索]`：semgrep 在该文件的命中（如有），请优先核验真伪，但不要局限于此
过长的文件会拆成多段分次送审，说明行会标注段号；跨段的问题只报一次

## 范围
- 只审查 diff 涉及的文件与改动行；忽略 *.lock、target/、build/、dist/、vendor/、自动生成代码、二进制文件

## 一、安全（最高优先级，对应 OWASP Top 10 / CERT Java）
- SQL 注入: 字符串拼接或格式化构造 SQL；MyBatis 使用 ${} 而非 #{}；必须参数化查询
- 反序列化: ObjectInputStream 原生反序列化、fastjson autoType、Jackson enableDefaultTyping、XMLDecoder
- 弱加密与弱随机: MD5/SHA1 存密码、DES/ECB 模式、安全场景（token/验证码/密钥）使用 java.util.Random 而非 SecureRandom
- XXE: XML 解析器（DocumentBuilderFactory/SAXParser）未禁用外部实体与 DTD
- 硬编码: 密钥/密码/token/内网地址写死在代码或仓库配置中
- 敏感信息泄漏: 日志或异常信息输出密码、token、身份证、手机号明文
- 越权与输入: 接口未校验资源归属（IDOR）、文件路径拼接未规范化（穿越风险）、重定向 URL 未白名单校验

## 二、正确性
- NPE: 链式调用与 Map.get 结果直接解引用；equals 应写为常量在前；Optional.get 裸调用
- 比较语义: BigDecimal 用 equals 而非 compareTo；Integer/Long 用 == 比较（缓存区间陷阱）；浮点数直接判等
- 异常处理: catch 后空块或仅打印；finally 中 return；捕获 Exception/Throwable 过宽；重抛时丢失 cause
- 并发: 共享 SimpleDateFormat/HashMap 等非线程安全对象；双重检查锁缺 volatile；无界队列线程池；遍历集合时结构化修改
- 事务: @Transactional 同类自调用或 private 方法失效；事务内执行 RPC/文件 IO；非 RuntimeException 默认不回滚的语义误用
- 资源: 流/连接/Channel 未使用 try-with-resources 关闭；ThreadLocal 未 remove

## 三、性能
- 循环内执行 DB 查询或 RPC（N+1）；循环内拼接字符串应用 StringBuilder
- 集合未预估初始容量；大结果集一次性载入内存；Pattern.compile 在循环内重复编译

## 四、Java 编码规范（阿里巴巴《Java 开发手册》黄山版 强制级全量对照）

> 以下 189 条为官方手册全部强制级规则（编号 R001-R306 可溯源，完整版含正反例见项目 rules_full.md）。
> 安全类问题以第一~三节为准；本节适用于命名、集合、并发、日志、MySQL、工程结构等官方强制项，命中按 major 处理，纯风格类降为 minor。

### 命名风格
- [R001] 所有编程相关的命名均不能以下划线或美元符号开始，也不能以下划线或美元符号结束。
- [R002] 所有编程相关的命名严禁使用拼音与英文混合的方式，更不允许直接使用中文的方式。
- [R003] 代码和注释中都要避免使用任何人类语言中的种族歧视性或侮辱性词语。
- [R004] 类名使用 UpperCamelCase 风格，以下情形例外：DO / PO / DTO / BO / VO / UID 等。
- [R005] 方法名、参数名、成员变量、局部变量都统一使用 lowerCamelCase 风格。
- [R006] 常量命名应该全部大写，单词间用下划线隔开，力求语义表达完整清楚，不要嫌名字长。
- [R007] 抽象类命名使用 Abstract 或 Base 开头；异常类命名使用 Exception 结尾，测试类命名以它要测试的类的名称开始，以 Test 结尾。
- [R008] 类型与中括号紧挨相连来定义数组。
- [R009] POJO 类中的任何布尔类型的变量，都不要加 is 前缀，否则部分框架解析会引起序列化错误。
- [R010] 包名统一使用小写，点分隔符之间有且仅有一个自然语义的英语单词。包名统一使用单数形式，但是类名如果有复数含义，类名可以使用复数形式。
- [R011] 避免在子父类的成员变量之间、或者不同代码块的局部变量之间采用完全相同的命名，使可理解性降低。
- [R012] 杜绝完全不规范的英文缩写，避免望文不知义。

### 常量定义
- [R019] 不允许任何魔法值（即未经预先定义的常量）直接出现在代码中。
- [R020] long 或 Long 赋值时，数值后使用大写 L，不能是小写 l，小写容易跟数字混淆，造成误解。
- [R021] 浮点数类型的数值后缀统一为大写的 D 或 F。

### 代码格式
- [R025] 如果大括号内为空，简洁地写成{}即可，大括号中间无需换行和空格；如果是非空代码块，则：1）左大括号前不换行。2）左大括号后换行。3）右大括号前换行。4）右大括号后还有 else 等代码则不换行；表示终止的右大括号后必须换行。
- [R026] 左小括号和右边相邻字符之间不需要空格；右小括号和左边相邻字符之间也不需要空格；而左大括号前需要加空格。详见第 5 条下方正例提示。
- [R027] if / for / while / switch / do 等保留字与左右括号之间都必须加空格。
- [R028] 任何二目、三目运算符的左右两边都需要加一个空格。
- [R029] 采用 4 个空格缩进，禁止使用 Tab 字符。
- [R030] 注释的双斜线与注释内容之间有且仅有一个空格。
- [R031] 在进行类型强制转换时，右括号与强制转换值之间不需要任何空格隔开。
- [R032] 单行字符数限制不超过 120 个，超出需要换行，换行时遵循如下原则：1）第二行相对第一行缩进 4 个空格，从第三行开始，不再继续缩进，参考示例。2）运算符与下文一起换行。3）方法调用的点符号与下文一起换行。4）方法调用中的多个参数需要换行时，在逗号后进行。5）在括号前不要换行，见反例。
- [R033] 方法参数在定义和传入时，多个参数逗号后面必须加空格。
- [R034] IDE 的 text file encoding 设置为 UTF-8；IDE 中文件的换行符使用 Unix 格式，不要使用Windows 格式。

### OOP 规约
- [R038] 避免通过一个类的对象引用访问此类的静态变量或静态方法，无谓增加编译器解析成本，直接用类名来访问即可。
- [R039] 所有的覆写方法，必须加 @Override 注解。
- [R040] 相同参数类型，相同业务含义，才可以使用的可变参数，参数类型避免定义为 Object。
- [R041] 外部正在调用的接口或者二方库依赖的接口，不允许修改方法签名，避免对接口调用方产生影响。接口过时必须加 @Deprecated 注解，并清晰地说明采用的新接口或者新服务是什么。
- [R042] 不能使用过时的类或方法。
- [R043] Object 的 equals 方法容易抛空指针异常，应使用常量或确定有值的对象来调用 equals。
- [R044] 所有整型包装类对象之间值的比较，全部使用 equals 方法比较。
- [R045] 任何货币金额，均以最小货币单位且为整型类型进行存储。
- [R046] 浮点数之间的等值判断，基本数据类型不能使用 == 进行比较，包装数据类型不能使用 equals进行判断。
- [R047] BigDecimal 的等值比较应使用 compareTo() 方法，而不是 equals() 方法。
- [R048] 定义数据对象 DO 类时，属性类型要与数据库字段类型相匹配。
- [R049] 禁止使用构造方法 BigDecimal(double) 的方式把 double 值转化为 BigDecimal 对象。
- [R050] 定义 DO / PO / DTO / VO 等 POJO 类时，不要设定任何属性默认值。
- [R051] 序列化类新增属性时，请不要修改 serialVersionUID 字段，避免反序列失败；如果完全不兼容升级，避免反序列化混乱，那么请修改 serialVersionUID 值。
- [R052] 构造方法里面禁止加入任何业务逻辑，如果有初始化逻辑，请放在 init 方法中。
- [R053] POJO 类必须写 toString 方法。使用 IDE 中的工具 source > generate toString 时，如果继承了另一个 POJO 类，注意在前面加一下 super.toString()。
- [R054] 禁止在 POJO 类中，同时存在对应属性 xxx 的 isXxx() 和 getXxx() 方法。

### 日期时间
- [R063] 日期格式化时，传入 pattern 中表示年份统一使用小写的 y。
- [R064] 在日期格式中分清楚大写的 M 和小写的 m，大写的 H 和小写的 h 分别指代的意义。
- [R065] 获取当前毫秒数：System.currentTimeMillis()；而不是 new Date().getTime()。
- [R066] 不允许在程序任何地方中使用：1）java.sql.Date 2）java.sql.Time 3）java.sql.Timestamp。
- [R067] 禁止在程序中写死一年为 365 天，避免在公历闰年时出现日期转换错误或程序逻辑错误。

### 集合处理
- [R070] 关于 hashCode 和 equals 的处理，遵循如下规则：1）只要覆写 equals，就必须覆写 hashCode。2）因为 Set 存储的是不重复的对象，依据 hashCode 和 equals 进行判断，所以 Set 存储的对象必须覆写这两种方法。3）如果自定义对象作为 Map 的键，那么必须覆写 hashCode 和 equals。
- [R071] 判断所有集合内部的元素是否为空，使用 isEmpty() 方法，而不是 size() == 0 的方式。
- [R072] 在使用 java.util.stream.Collectors 类的 toMap() 方法转为 Map 集合时，一定要使用参数类型为 BinaryOperator，参数名为 mergeFunction 的方法，否则当出现相同 key 时会抛出IllegalStateException 异常。
- [R073] 在使用 java.util.stream.Collectors 类的 toMap() 方法转为 Map 集合时，一定要注意当 value为 null 时会抛 NPE 异常。
- [R074] ArrayList 的 subList 结果不可强转成 ArrayList，否则会抛出 ClassCastException 异常：java.util.RandomAccessSubList cannot be cast to java.util.ArrayList。
- [R075] 使用 Map 的方法 keySet() / values() / entrySet() 返回集合对象时，不可以对其进行添加元素操作，否则会抛出 UnsupportedOperationException 异常。
- [R076] Collections 类返回的对象，如：emptyList() / singletonList() 等都是 immutable list，不可对其进行添加或者删除元素的操作。
- [R077] 在 subList 场景中，高度注意对父集合元素的增加或删除，均会导致子列表的遍历、增加、删除产生 ConcurrentModificationException 异常。
- [R078] 使用集合转数组的方法，必须使用集合的 toArray(T[] array)，传入的是类型完全一致、长度为0 的空数组。
- [R079] 使用 Collection 接口任何实现类的 addAll() 方法时，要对输入的集合参数进行 NPE 判断。
- [R080] 使用工具类 Arrays.asList() 把数组转换成集合时，不能使用其修改集合相关的方法，它的 add/ remove / clear 方法会抛出 UnsupportedOperationException 异常。
- [R081] 泛型通配符<? extends T>来接收返回的数据，此写法的泛型集合不能使用 add 方法，而<? super T>不能使用 get 方法，两者在接口调用赋值的场景中容易出错。
- [R082] 在无泛型限制定义的集合赋值给泛型限制的集合时，在使用集合元素时，需要进行instanceof 判断，避免抛出 ClassCastException 异常。
- [R083] 不要在 foreach 循环里进行元素的 remove / add 操作。remove 元素请使用 iterator 方式，如果并发操作，需要对 iterator 对象加锁。
- [R084] 在 JDK7 版本及以上，Comparator 实现类要满足如下三个条件，不然 Arrays.sort，Collections.sort 会抛 IllegalArgumentException 异常。

### 并发处理
- [R091] 获取单例对象需要保证线程安全，其中的方法也要保证线程安全。
- [R092] 创建线程或线程池时请指定有意义的线程名称，方便出错时回溯。
- [R093] 线程资源必须通过线程池提供，不允许在应用中自行显式创建线程。
- [R094] 线程池不允许使用 Executors 去创建，而是通过 ThreadPoolExecutor 的方式，这样的处理方式让写的同学更加明确线程池的运行规则，规避资源耗尽的风险。
- [R095] SimpleDateFormat 是线程不安全的类，一般不要定义为 static 变量，如果定义为 static，必须加锁，或者使用 DateUtils 工具类。
- [R096] 必须回收自定义的 ThreadLocal 变量记录的当前线程的值，尤其在线程池场景下，线程经常会被复用，如果不清理自定义的 ThreadLocal 变量，可能会影响后续业务逻辑和造成内存泄露等问题。尽量在代码中使用 try-finally 块进行回收。
- [R097] 高并发时，同步调用应该去考量锁的性能损耗。能用无锁数据结构，就不要用锁；能锁区块，就不要锁整个方法体；能用对象锁，就不要用类锁。
- [R098] 对多个资源、数据库表、对象同时加锁时，需要保持一致的加锁顺序，否则可能会造成死锁。
- [R099] 在使用阻塞等待获取锁的方式中，必须在 try 代码块之外，并且在加锁方法与 try 代码块之间没有任何可能抛出异常的方法调用，避免加锁成功后，在 finally 中无法解锁。说明一：在 lock 方法与 try 代码块之间的方法调用抛出异常，无法解锁，造成其它线程无法成功获取锁。说明二：如果 lock 方法在 try 代码块之内，可能由于其它方法抛出异常，导致在 finally 代码块中，unlock 对未加锁的对象解锁，它会调用 AQS 的 tryRelease 方法（取决于具体实现类），抛出 IllegalMonitorStateException 异常。说明三：在 Lock 对象的 lock 方法实现中可能抛出 unchecked 异常，产生的后果与说明二相同。
- [R100] 在使用尝试机制来获取锁的方式中，进入业务代码块之前，必须先判断当前线程是否持有锁。锁的释放规则与锁的阻塞等待方式相同。
- [R101] 并发修改同一记录时，避免更新丢失，需要加锁。要么在应用层加锁，要么在缓存加锁，要么在数据库层使用乐观锁，使用 version 作为更新依据。
- [R102] 多线程并行处理定时任务时，Timer 运行多个 TimeTask 时，只要其中之一没有捕获抛出的异常，其它任务便会自动终止运行，使用 ScheduledExecutorService 则没有这个问题。

### 控制语句
- [R110] 在一个 switch 块内，每个 case 要么通过 continue / break / return 等来终止，要么注释说明程序将继续执行到哪一个 case 为止；在一个 switch 块内，都必须包含一个 default 语句并且放在最后，即使它什么代码也没有。
- [R111] 当 switch 括号内的变量类型为 String 并且此变量为外部参数时，必须先进行 null 判断。
- [R112] 在 if / else / for / while / do 语句中必须使用大括号。
- [R113] 三目运算符 condition ? 表达式 1：表达式 2 中，高度注意表达式 1 和 2 在类型对齐时，可能抛出因自动拆箱导致的 NPE 异常。
- [R114] 在高并发场景中，避免使用“等于”判断作为中断或退出的条件。

### 注释规约
- [R124] 类、类属性、类方法的注释必须使用 Javadoc 规范，使用 /** 内容 */ 格式，不得使用 // xxx方式。
- [R125] 所有的抽象方法（包括接口中的方法）必须要用 Javadoc 注释、除了返回值、参数异常说明外，还必须指出该方法做什么事情，实现什么功能。
- [R126] 所有的类都必须添加创建者和创建日期。
- [R127] 方法内部单行注释，在被注释语句上方另起一行，使用 // 注释。方法内部多行注释使用 /* */注释，注意与代码对齐。
- [R128] 所有的枚举类型字段必须要有注释，说明每个数据项的用途。

### 前后端规约
- [R136] 前后端交互的 API，需要明确协议、域名、路径、请求方法、请求内容、状态码、响应体。
- [R137] 前后端数据列表相关的接口返回，如果为空，则返回空数组[]或空集合{}。
- [R138] 服务端发生错误时，返回给前端的响应信息必须包含 HTTP 状态码，errorCode、errorMessage、用户提示信息四个部分。
- [R139] 在前后端交互的 JSON 格式数据中，所有的 key 必须为小写字母开始的 lowerCamelCase风格，符合英文表达习惯，且表意完整。
- [R140] errorMessage 是前后端错误追踪机制的体现，可以在前端输出到 type="hidden" 文字类控件中，或者用户端的日志中，帮助我们快速地定位出问题。
- [R141] 对于需要使用超大整数的场景，服务端一律使用 String 字符串类型返回，禁止使用 Long 类型。
- [R142] HTTP 请求通过 URL 传递参数时，不能超过 2048 字节。
- [R143] HTTP 请求通过 body 传递内容时，必须控制长度，超出最大长度后，后端解析会出错。
- [R144] 在翻页场景中，用户输入参数的小于 1，则前端返回第一页参数给后端；后端发现用户输入的参数大于总页数，直接返回最后一页。
- [R145] 服务器内部重定向必须使用 forward；外部重定向地址必须使用 URL 统一代理模块生成，否则会因线上采用 HTTPS 协议而导致浏览器提示“不安全”，并且还会带来 URL 维护不一致的问题。

### 其他
- [R150] 在使用正则表达式时，利用好其预编译功能，可以有效加快正则匹配速度。
- [R151] 避免用 ApacheBeanutils 进行属性的 copy。
- [R152] velocity 调用 POJO 类的属性时，直接使用属性名取值即可，模板引擎会自动按规范调用 POJO的 getXxx()，如果是 boolean 基本数据类型变量（boolean 命名不需要加 is 前缀），会自动调 isXxx()方法。
- [R153] 后台输送给页面的变量必须加 $!{var} ——中间的感叹号。
- [R154] 注意 Math.random() 这个方法返回是 double 类型，注意取值的范围 0 ≤ x < 1（能够取到零值，注意除零异常），如果想获取整数类型的随机数，不要将 x 放大 10 的若干倍然后取整，直接使用 Random 对象的 nextInt 或者 nextLong 方法。
- [R155] 枚举 enum（括号内）的属性字段必须是私有且不可变。

### 错误码
- [R159] 错误码的制定原则：快速溯源、沟通标准化。
- [R160] 错误码不体现版本号和错误等级信息。
- [R161] 全部正常，但不得不填充错误码时返回五个零：00000。
- [R162] 错误码为字符串类型，共 5 位，分成两个部分：错误产生来源+四位数字编号。
- [R163] 编号不与公司业务架构，更不与组织架构挂钩，以先到先得的原则在统一平台上进行，审批生效，编号即被永久固定。
- [R164] 错误码使用者避免随意定义新的错误码。
- [R165] 错误码不能直接输出给用户作为提示信息使用。

### 异常处理
- [R172] Java 类库中定义的可以通过预检查方式规避的 RuntimeException 异常不应该通过 catch 的方式来处理，比如：NullPointerException，IndexOutOfBoundsException 等等。
- [R173] 异常捕获后不要用来做流程控制，条件控制。
- [R174] catch 时请分清稳定代码和非稳定代码，稳定代码指的是无论如何不会出错的代码。对于非稳定代码的 catch 尽可能进行区分异常类型，再做对应的异常处理。
- [R175] 捕获异常是为了处理它，不要捕获了却什么都不处理而抛弃之，如果不想处理它，请将该异常抛给它的调用者。最外层的业务使用者，必须处理异常，将其转化为用户可以理解的内容。
- [R176] 事务场景中，抛出异常被 catch 后，如果需要回滚，一定要注意手动回滚事务。
- [R177] finally 块必须对资源对象、流对象进行关闭，有异常也要做 try-catch。
- [R178] 不要在 finally 块中使用 return
- [R179] 捕获异常与抛异常，必须是完全匹配，或者捕获异常是抛异常的父类。
- [R180] 在调用 RPC、二方包、或动态生成类的相关方法时，捕捉异常使用 Throwable 类进行拦截。

### 日志规约
- [R185] 应用中不可直接使用日志系统（Log4j、Logback）中的 API，而应依赖使用日志框架（SLF4J、JCL—Jakarta Commons Logging）中的 API，使用门面模式的日志框架，有利于维护和各个类的日志处理方式统一。
- [R186] 日志文件至少保存 15 天，因为有些异常具备以“周”为频次发生的特点。对于当天日志，以“应用名.log”来保存，保存在/{统一目录}/{应用名}/logs/目录下，过往日志格式为：{logname}.log.{保存日期}，日期格式：yyyy-MM-dd
- [R187] 根据国家法律，网络运行状态、网络安全事件、个人敏感信息操作等相关记录，留存的日志不少于六个月，并且进行网络多机备份。
- [R188] 应用中的扩展日志（如打点、临时监控、访问日志等）命名方式：appName_logType_logName.log。logType：日志类型，如 stats / monitor / access 等；logName：日志描述。这种命名的好处：通过文件名就可知道日志文件属于什么应用，什么类型，什么目的，也有利于归类查找。
- [R189] 在日志输出时，字符串变量之间的拼接使用占位符的方式。
- [R190] 对于 trace / debug / info 级别的日志输出，必须进行日志级别的开关判断：
- [R191] 避免重复打印日志，浪费磁盘空间，务必在日志配置文件中设置 additivity=false
- [R192] 生产环境禁止使用 System.out 或 System.err 输出或使用 e.printStackTrace() 打印异常堆栈。
- [R193] 异常信息应该包括两类信息：案发现场信息和异常堆栈信息。如果不处理，那么通过关键字throws 往上抛出。
- [R194] 日志打印时禁止直接用 JSON 工具将对象转换成 String。

### 
- [R199] 好的单元测试必须遵守 AIR 原则。
- [R200] 单元测试应该是全自动执行的，并且非交互式的。测试用例通常是被定期执行的，执行过程必须完全自动化才有意义。输出结果需要人工检查的测试不是一个好的单元测试。不允许使用 System.out 来进行人肉验证，单元测试必须使用 assert 来验证。
- [R201] 保持单元测试的独立性。为了保证单元测试稳定可靠且便于维护，单元测试用例之间决不能互相调用，也不能依赖执行的先后次序。
- [R202] 单元测试是可以重复执行的，不能受到外界环境的影响。
- [R203] 对于单元测试，要保证测试粒度足够小，有助于精确定位问题。单测粒度至多是类级别，一般是方法级别。
- [R204] 核心业务、核心应用、核心模块的增量代码确保单元测试通过。
- [R205] 单元测试代码必须写在如下工程目录： src/test/java，不允许写在业务代码目录下。
- [R215] 隶属于用户个人的页面或者功能必须进行权限控制校验。
- [R216] 用户敏感数据禁止直接展示，必须对展示数据进行脱敏。
- [R217] 用户输入的 SQL 参数严格使用参数绑定或者 METADATA 字段值限定，防止 SQL 注入，禁止字符串拼接 SQL 访问数据库。
- [R218] 用户请求传入的任何参数必须做有效性验证。
- [R219] 禁止向 HTML 页面输出未经安全过滤或未正确转义的用户数据。
- [R220] 表单、AJAX 提交必须执行 CSRF 安全验证。
- [R221] URL 外部重定向传入的目标地址必须执行白名单过滤。
- [R222] 在使用平台资源，譬如短信、邮件、电话、下单、支付，必须实现正确的防重放的机制，如数量限制、疲劳度控制、验证码校验，避免被滥刷而导致资损。
- [R223] 对于文件上传功能，需要对于文件大小、类型进行严格检查和控制。
- [R224] 配置文件中的密码需要加密。
- [R300] 存储方案和底层数据结构的设计获得评审一致通过，并沉淀成为文档。
- [R301] 在需求分析阶段，如果与系统交互的 User 超过一类并且相关的 UseCase 超过 5 个，使用用例图来表达更加清晰的结构化需求。
- [R302] 如果某个业务对象的状态超过 3 个，使用状态图来表达并且明确状态变化的各个触发条件。
- [R303] 如果系统中某个功能的调用链路上的涉及对象超过 3 个，使用时序图来表达并且明确各调用环节的输入与输出。
- [R304] 如果系统中模型类超过 5 个，且存在复杂的依赖关系，使用类图来表达并且明确类之间的关系。
- [R305] 如果系统中超过 2 个对象之间存在协作关系，并需要表示复杂的处理流程，使用活动图来表示。
- [R306] 系统设计时要准确识别出弱依赖，并针对性地设计降级和应急预案，保证核心系统正常可用。

### 建表规约
- [R226] 表达是与否概念的字段，必须使用 is_xxx 的方式命名，数据类型是 unsigned tinyint（1 表示是，0 表示否）。
- [R227] 表名、字段名必须使用小写字母或数字，禁止出现数字开头禁止两个下划线中间只出现数字。数据库字段名的修改代价很大，因为无法进行预发布，所以字段名称需要慎重考虑。
- [R228] 表名不使用复数名词。
- [R229] 禁用保留字，如 desc、range、match、delayed 等，请参考 MySQL 官方保留字。
- [R230] 主键索引名为 pk_字段名；唯一索引名为 uk_字段名；普通索引名则为 idx_字段名。
- [R231] 小数类型为 decimal，禁止使用 float 和 double。
- [R232] 如果存储的字符串长度几乎相等，使用 char 定长字符串类型。
- [R233] varchar 是可变长字符串，不预先分配存储空间，长度不要超过 5000，如果存储长度大于此值，定义字段类型为 text，独立出来一张表，用主键来对应，避免影响其它字段索引率。
- [R234] 表必备三字段：id，create_time，update_time。
- [R235] 在数据库中不能使用物理删除操作，要使用逻辑删除。

### 索引规约
- [R242] 业务上具有唯一特性的字段，即使是组合字段，也必须建成唯一索引。
- [R243] 超过三个表禁止 join。需要 join 的字段，数据类型保持绝对一致；多表关联查询时，保证被关联的字段需要有索引。
- [R244] 在 varchar 字段上建立索引时，必须指定索引长度，没必要对全字段建立索引，根据实际文本区分度决定索引长度。
- [R245] 页面搜索严禁左模糊或者全模糊，如果需要请走搜索引擎来解决。

### SQL 语句
- [R253] 不要使用 count(列名) 或 count(常量) 来替代 count(*)，count(*) 是 SQL92 定义的标准统计行数的语法，跟数据库无关，跟 NULL 和非 NULL 无关。
- [R254] count(distinct col) 计算该列除 NULL 之外的不重复行数，注意 count(distinct col1 , col2) 如果其中一列全为 NULL，那么即使另一列有不同的值，也返回为 0。
- [R255] 当某一列的值全是 NULL 时，count(col) 的返回结果为 0；但 sum(col) 的返回结果为 NULL，因此使用 sum() 时需注意 NPE 问题。
- [R256] 使用 ISNULL() 来判断是否为 NULL 值。
- [R257] 代码中写分页查询逻辑时，若 count 为 0 应直接返回，避免执行后面的分页语句。
- [R258] 不得使用外键与级联，一切外键概念必须在应用层解决。
- [R259] 禁止使用存储过程，存储过程难以调试和扩展，更没有移植性。
- [R260] 数据订正（特别是删除或修改记录操作）时，要先 select，避免出现误删除的情况，确认无误才能执行更新语句。
- [R261] 对于数据库中表记录的查询和变更，只要涉及多个表，都需要在列名前加表的别名（或表名）进行限定。

### ORM 映射
- [R266] 在表查询中，一律不要使用 * 作为查询的字段列表，需要哪些字段必须明确写明。
- [R267] POJO 类的布尔属性不能加 is，而数据库字段必须加 is_，要求在 resultMap 中进行字段与属性之间的映射。
- [R268] 不要用 resultClass 当返回参数，即使所有类属性名与数据库字段一一对应，也需要定义<resultMap>；反过来，每一个表也必然有一个<resultMap>与之对应。
- [R269] sql.xml 配置参数使用：#{}，#param# 不要使用 ${} 此种方式容易出现 SQL 注入。
- [R270] iBATIS 自带的 queryForList(String statementName，int start，int size) 不推荐使用。
- [R271] 不允许直接拿 HashMap 与 Hashtable 作为查询结果集的输出。
- [R272] 更新数据表记录时，必须同时更新记录对应的 update_time 字段值为当前时间。

### 二方库依赖
- [R279] 定义 GAV 遵从以下规则：1）GroupId 格式：com.{公司/BU}.业务线.[子业务线]，最多 4 级。
- [R280] 二方库版本号命名方式：主版本号.次版本号.修订号1）主版本号：产品方向改变，或者大规模 API 不兼容，或者架构不兼容升级。2）次版本号：保持相对兼容性，增加主要功能特性，影响范围极小的 API 不兼容修改。3）修订号：保持完全兼容性，修复 BUG、新增次要功能特性等。
- [R281] 线上应用不要依赖 SNAPSHOT 版本（安全包除外）；正式发布的类库必须先去中央仓库进行查证，使 RELEASE 版本号有延续性，且版本号不允许覆盖升级。
- [R282] 二方库的新增或升级，保持除功能点之外的其它 jar 包仲裁结果不变。如果有改变，必须明确评估和验证。
- [R283] 二方库里可以定义枚举类型，参数可以使用枚举类型，但是接口返回值不允许使用枚举类型或者包含枚举类型的 POJO 对象。
- [R284] 二方库定制包的命名方式，在规定的版本号之后加“-英文说明[序号]”，英文说明可以是部门简称、业务名称，序号直接紧跟在英文说明之后，表示此定制包的顺序号。
- [R285] 依赖于一个二方库群时，必须定义一个统一的版本变量，避免版本号不一致。
- [R286] 禁止在子项目的 pom 依赖中出现相同的 GroupId，相同的 ArtifactId，但是不同的 Version。

## 严重级别定义
- blocker: 安全漏洞（注入/反序列化/弱加密/硬编码密钥/越权/XXE）或数据损坏
- major: 明确逻辑缺陷（NPE、并发错误、事务失效、异常吞没、资源泄漏）
- minor: 性能问题、规范偏离
- info: 风格与可读性建议
